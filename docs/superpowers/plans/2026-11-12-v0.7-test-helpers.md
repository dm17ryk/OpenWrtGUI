# OpenWrtGUI v0.7 Test helpers (step-through, frame analysis, channel analysis) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The test helpers of spec 7.2 and 7.3: the Wi-Fi **step-through** runner (every ticked mode × channel × power, one pure mode per step, each step proven on air before its dwell, advanced on a timer, by hand or when a station re-joins, the radio restored at the end), **frame analysis** through the monitor interface (rate mix per direction, signal histogram, retry-flag share, bad-FCS share) and **channel analysis** (a scan of nearby networks and the channel survey per channel, LuCI's Status › Channel analysis). The updater asks before it stops one of them (spec 9.3). The plan also closes, on AP2, the two v0.6 hardware items that can be closed there (the O19 reboot and a restore) and says why the third (the HTTPS redirect) stays open. After this plan 0.7.0 can be released.

**Architecture:** The helpers reuse the paths the app already has:
- **Step-through** (`wifi/steps.py`, `wifi/step_service.py`):
  - Each step is a Wi-Fi Apply of one mode, one channel and optionally one TX power. It goes through `WifiService` (the same compile, exact preview lines, write lock, audit and full proof, beacon rate included).
  - A new `StepService` runs the steps as a background job, one per router.
  - The radio's own options are saved to the data folder before step 1 and applied back at the end.
- **Channel analysis** (`rf/scan.py`, `rf/scan_service.py`):
  - A passive `iw` scan, on the AP interface (`ap-force`) when the radio is on air, or on a temporary `owgscan0` when it is parked.
  - Survey dumps taken before and after the scan give each channel's busy share.
- **Frame analysis** (`rf/frames.py`, `rf/frames_service.py`):
  - Short `tcpdump` windows on `owgmon0`, parsed on the PC.
  - The results are published on the RF live socket the screen already uses.
- **Shared monitor:** `owgmon0` becomes a shared, counted resource (`wifi/monitor.py`) for the beacon check, Capture on mon0 and frame analysis. Today two of them start with `iw dev owgmon0 del`.

**Tech Stack:** as v0.6c (Python 3.13, FastAPI, asyncssh, pydantic 2; React 19, TypeScript, Vite, TanStack Query, vitest, Playwright). No new dependency, and nothing installed on a router.

## Rules (the decisions the code must follow)

- **Names in commands.** Interface names from `iw dev` or ubus status must fullmatch `[A-Za-z0-9._-]{1,15}` before they go into a command. A radio name fullmatches `[A-Za-z0-9_]{1,15}` and must be a radio of the router. A MAC is `[0-9a-f]{2}(:[0-9a-f]{2}){5}` after lowercasing. Channels and powers come only from the radio's `RadioLimits`.
- **Frequency to channel:** 2412-2472 MHz → `(f - 2407) / 5`; 2484 → 14; 5150-5895 → `(f - 5000) / 5`; 5955-7115 → `(f - 5950) / 5`; anything else → `None`.
- **A BSS's occupied band** is `[centre - width/2, centre + width/2]`. The centre is the primary channel's frequency for 20 MHz, ±10 MHz for 40 MHz (secondary above or below). A channel counts a BSS as overlapping when the channel's centre frequency lies strictly inside that band. A 20 MHz BSS on channel 6 overlaps channels 5, 6 and 7.
- **Own BSSIDs** are the `addr` of every interface of type AP on the router, from `iw dev`.
- **A frame's direction** comes from its source (`SA:` or `TA:`):
  - TX from AP: the source is one of the radio's BSSIDs.
  - RX at AP: another address sent it, and its `BSSID:`, `DA:` or `RA:` is one of them.
  - Anything else counts only in the totals (frames heard, bad FCS).
- **Busy errors.** `RouterBusy` (`src/openwrtgui/busy.py`, Task 1) maps to 409 in `api/errors.py`, beside `PreviewChanged` (Task 8). `RadioBusy` (`wifi/service.py`), `StepBusy` (`wifi/step_service.py`) and `FlashBusy` (`flash/service.py`) subclass it, so the one handler covers them.
- **Change lines.** `WifiPlan.change_lines` is `lines` without the TX-mask line (`iw dev … set bitrates …`), so its interface name never decides a comparison (D3).

**Runner, per job** (one `asyncio.Task`, the radio held with `hold_radio` for the whole job):
1. **Start.** Write the saved file atomically (temporary file, then rename); open the CSV (header `step,mode,channel,txpower_dbm,proven,failed_checks,beacon,rejoin_s,started,ended`).
2. **For each step:**
   1. Phase "applying". `wifi.plan(...)`, whose `change_lines` must equal the preview's; otherwise stop with "changed during the step-through" and restore.
   2. `wifi.apply(router_id, req, digest=plan.digest, holder=token)`.
   3. An `error`: guard live → D7; otherwise stop and restore (D4). Not verified → record "not proven", go to the next step (D4).
   4. Advance:
      - timer: "dwell" `dwell_s`;
      - manual: "waiting for Next";
      - rejoin: "waiting for station". Read `get_clients` each tick until `joined` or the limit, then "dwell".
   5. During every wait, each tick checks Stop, Next and the guard (live → D7 at once).
   6. Write the CSV row.
3. **End.** After the last step, or on Stop: phase "restoring", `wifi.apply_ops(router_id, radio, saved_ops(...), holder=token)`. Then:
   - proven: delete the saved file, phase "done" or "stopped";
   - not proven: phase "failed", `restore_pending` True, the file kept.
4. **D7.** Phase "stopped", `restore_pending` True, the file kept, `error` naming the run.
