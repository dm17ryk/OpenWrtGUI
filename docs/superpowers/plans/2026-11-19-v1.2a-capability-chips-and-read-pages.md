# v1.2a: Capability Chips and the Read-Only Tool Pages Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for
> tracking.

**Goal:** Discovery shows each router's capabilities as chips that open their pages, and a new per-router
**Tools** screen adds the first two tool pages, Port statistics and Connections, both read only.

**Architecture:**
- **Chips:** `capability_map()` (`discovery/capabilities.py`) already reaches the browser in
  `DiscoveryState.capabilities`, but no screen shows it. A new Discovery section draws one chip per row. A
  frontend table maps a capability to the screen that uses it.
- **Tools screen:** `/routers/:id/tools/:tool`, one tab per tool page. 1.2a adds `port-stats` and `connections`;
  1.2b adds the active pages.
- **Port statistics:** the per-port MIB counters that `swconfig dev <switch> show` already prints (the Ports
  screen reads the same command), parsed into packets, bytes and errors, read every 5 s while the tab is open.
  Rates come from two reads.
- **Connections:** the System screen's connection read (`/proc/net/nf_conntrack`, first 500 lines) gains each
  entry's conntrack helper and the table's size, and a separate read gives the SIP ALG state from the fw4
  ruleset.
- No router writes and no AP2 window: everything is read from commands AP2 has already answered in
  `tests/fixtures/ap2/`.

**Tech Stack:** Python 3.13, FastAPI, pydantic, asyncio, pytest; React + TypeScript, TanStack Query, Vitest,
Playwright.

**Spec:**
- `docs/superpowers/specs/2026-11-03-openwrt-gui-design.md`, 7.8 "Phase 2" (D17): each capability chip links to its
  own tool page; the pages are Throughput, Air survey, Station management, Traffic generator, Port statistics
  ("`ethtool` and switch MIB counters"), Connections ("`conntrack`, SIP ALG toggle").
- `docs/superpowers/plans/2026-11-17-1.x-inventory-and-split.md`, section 4: 1.2a is the chips and the read-only
  or existing pages (Port statistics, Connections, Air survey linked to Channel analysis); 1.2b is the active
  pages. Dmitry answered D1 (order 1.1, 1.2, 1.3) "All recommended" on 2026-11-17, and "Yes, write it" for this
  plan on 2026-11-19.

**Base:** branch `feat/v1.2-tool-pages` from master 8f34087 (1.2.0-dev), worktree `.claude/worktrees/v12`, local.

## Review Focus

1. **A counter wraps or resets between two reads.** `prev 4294967000, cur 500` gives a rate from the wrap.
   `prev 900, cur 100` gives "reset". Neither shows a negative or 10-digit rate. Test in Task 5.
2. **An odd `show`:** a port with no MIB lines, a counter value of `???`, a driver with other counter names, a
   `show` that failed. Each port still appears: "No counters" when it has none, unknown names under All counters
   only. A failed read says "Could not read the switch counters: <detail>". Test in Task 3.
3. **Odd conntrack lines:** IPv6, `[UNREPLIED]`, `[ASSURED]`, ICMP without ports, `helper=sip`, a missing
   `nf_conntrack_count`. Rows parse, `helper` is `None` when absent, and a missing count gives `total=None` with
   the table still shown. Test in Task 6.
4. **An odd ruleset:** no `table inet fw4`; `ct helper set "sip"` in two zones; a helper rule for another protocol
   (`"ftp"`). These give unknown; on with both zones; off, because ftp is not SIP. Test in Task 6.
5. **The tab is left open, or the router goes away.** Reads run only while the tab is open and the window is
   visible. A failed read keeps the last counters with the error above them, and the rates go blank. Test in
   Task 5.

## 1.2b: decisions to answer before its plan

1.2b holds the pages that write or send traffic. Each needs an answer from Dmitry. The recommendations follow the
patterns 1.0-1.1 already use.

| # | Decision | Recommended | The other choice |
|---|---|---|---|
| B1 | **Throughput: the other end** | The router runs `iperf3` (AP2 has iperf3 3.x, not iperf 2), as client to a host and port you name (`-J` for JSON results, at most 60 s), or as a one-shot server (`-s -1`) that you test from your own iperf3. The app ships no iperf3 for Windows. | Bundle `iperf3.exe` so the PC is always the other end. |
| B2 | **Traffic from the router during a harness run** | Throughput, Traffic generator and Station management count as writes: refused during a run, and stopped if a run starts mid-way. Bench Guard's own lock file is the harness's iperf sweep, so router traffic would skew it. | Allow them during a run with a warning. |
| B3 | **Traffic generator (socat): what it does** | Two modes, at most 300 s each. **Listen**: the router listens on a TCP or UDP port and shows what arrives (peers, bytes, the first 64 bytes in hex). **Send**: the router sends N bytes or a line of text to an address and port. This checks firewall rules and port forwards from both sides. socat cannot set a rate, so this is not a load generator. | A load generator from another tool (none on AP2's image today). |
| B4 | **SIP ALG switch** | Through the firewall's uci write, with the usual 60 s rollback. For each zone: `auto_helper '0'` plus a `list helper` of the zone's other helpers, so SIP stops and the other helpers keep going. Switching back restores the zone as it was. | Unload `nf_nat_sip`/`nf_conntrack_sip` at runtime (fails while fw4 references the helper, and comes back at boot). |
| B5 | **Station management: transport and actions** | Over hostapd's ubus, which Deauth already uses. AP2's hostapd offers `bss_transition_request`, `rrm_nr_get_own`, `rrm_nr_list`, `rrm_nr_set` and `rrm_beacon_req` (recorded in `ap2/wifi_on.json`). Actions: **Send BSS transition request** (to another BSS you pick), **Neighbour report** (read the list; set it from the bench's other APs), **Beacon report request**. Each is a write; its preview names the station. `hostapd_cli` is not used. | `hostapd_cli` commands, as the spec's line names them. |
| B6 | **The AP2 window for 1.2b** | One window of about 45 minutes with your OK at the time, Bench Guard clear and the txctl session told first: Throughput against your PC, Traffic generator both ways, the SIP ALG switch and back (proven by the ruleset), and Station management with the radio on air (OwgTest, channel 11) and the bench phone. | Two windows (wired, then radio). |
| B7 | **Execution of 1.2a** | Native, then one fresh reviewer on the most capable model, as for 1.1a (eight tasks, no writes, no router). | Subagent-driven, with a review per task. |

1.2b's plan is written once B1-B7 are answered. It ends with the 1.2.0 release, each step on Dmitry's go.
